# V1 开发验收：固定 32 个牌山根组

本批只判断 V1 是否可以冻结为 V2 的实验对照。V0 继续作为线上默认；不以本批宣称积分提高、统计不劣或完成发布验收。

## 冻结与检查标准

- 生产代码基点为 `36b7aca`；逐文件哈希见 `freeze.json`。规则、模拟器、两版策略和生产评估器均不修改。
- `experiment.json` 在运行前固定 32 个新根组，每组四种换座，V0/V1 各续打一桌，共 256 个桌赛、每桌 8 单局。沿用 E3 对手池：两名 V0、一名 V1。历史身份名 `opp-v0` 实际使用 V1，以 `name` 为准。
- 使用逻辑时钟。运行耗时只供资源估算，不能作为动作窗口时限证据。
- 固定全部样本，不按分数提前择优停止，不删去错误桌赛。若出现故障，先诊断，明确记录实验是否有效。
- 开发验收要求：已知故障回归通过；冻结检查通过；运行故障均已解释并解决；相同请求的计划差异可归因于 V1 预定修复。完整桌赛积分和区间如实报告，有系统性负向迹象时先调查。
- 正式发布另需预先声明的不劣/改善判断标准、实际部署环境的并发测试房验收和目标赛事格式验证；本批不替代这些检查。

## 同输入比较如何工作

`run_seed.py` 调用实际 `scripts/evaluate.py` 的工厂和完整桌赛入口，只在待测座位包裹现有 `choose()` 接口。实际策略原计划仍用于推进；旁路用相同 `DecisionRequest` 比较另一策略。双方各自轨迹上的待测窗口都检查，但这些请求不是独立的效果统计样本。

比较候选动作顺序和数值评分，忽略预期变化的理由文案。分歧时保留完整请求、预算及两份计划。缺失规则事实和旁路异常均显式记录；旁路不读取 `WorldState`。`test_harness.py` 验证实际计划未被替换、缺失事实可记录、旁路异常不改变实际动作。

## 运行与产物

在仓库根目录执行一个根组（`--out` 必须是新目录）：

```bash
.venv/bin/python tests/offline/evidence/v1-acceptance-2026-09-06/run_seed.py \
  --seed-index 0 --out runs/v1-acceptance-2026-09-06/seed-00
```

每个根组独立保存原评估器的 `experiment.json/results.jsonl/report.json/report.md/manifest.json`，以及：

| 文件 | 用途与限制 |
| --- | --- |
| `comparison.json` | 同输入比较总数、动作窗口类型、候选事实类型、分歧与异常计数；持续时间单位为秒 |
| `decisions.jsonl` | 仅分歧请求；结合非零比较总数与零分歧计数，空文件表示没有观察到分歧。`request` 只含玩家可见信息，预算是原进程单调时钟秒值，跨进程比较须平移；不是完整牌谱或训练完整世界 |
| `completed.json` | CLI 正常返回并完成源码冻结复核的标记；不代表所有桌赛完赛或策略验收通过 |

中断目录保持原样。重跑使用另一个新目录，并在汇总时明确选择对应的有效尝试，不能覆盖原故障证据。大文件保存在忽略目录 `runs/`，完成后将紧凑报告、结果、覆盖统计与归档哈希放回本目录。跨机器迁移时携带实验配置、冻结清单、脚本和原始产物，使用同一代码提交；不要只搬报告截图。

整批执行或复用完整检查点（默认两进程，最多四进程）：

```bash
.venv/bin/python tests/offline/evidence/v1-acceptance-2026-09-06/run_batch.py \
  --out runs/v1-acceptance-2026-09-06 --workers 4
```

批量脚本只复用带完成标记且配置吻合的根组；不会跳过中断目录。汇总同时保存每个根组的 manifest 和文件哈希。旁路脚本冻结指纹在 `freeze.json` 的 `harness_sha256` 中，迁移时也应核对。

本批的初始庄家固定为待测逻辑身份，循环换座并未扩展相对初始庄位；对称输入可能重复产生相同轨迹。报告以 32 个根组为聚类单位，不把 128 对桌赛或决策次数当作独立样本。本批配置不覆盖所有规则开关或外部对手风格。

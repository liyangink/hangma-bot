# `application` 模块实施规范

## 目标与边界

本模块拥有一个身份的完整赛事生命周期、多场并发、截止时间和降级循环。先阅读根规范、接口协议、验收门禁和 `doc/implementation/modules/application.md`。

- 一个 `ParticipantRuntime` 恰好对应一个 Token；正式赛事启动一个，测试房间用四个隔离进程各启动一个。
- 以 `active_games` 为权威动态维护最多 `config.M` 个场次，不能预建固定数量，也不能把空列表当赛事结束。
- 应用层把 `ObservedActionWindow`、`HangmaRules.analyze()` 和赛事上下文组装成 `DecisionRequest`；适配器不得替它完成。
- 先得到紧急动作，再运行主策略；最终动作提交前调用规则模块复核。
- `ActionGate`、每 Token 请求调度器、HTTP 连接池和序号恢复都属于官方适配器，应用层不得复制。
- 第一阶段只做场次任务监督和简单外部进程重启，不引入通用工作流、事件总线或分布式任务系统。

## 提交与生命周期不变量

- 任意时刻同一场次最多一个在途提交。
- 只有 `SubmitRejectedRetryable` 才允许在同一原始预算内排除已拒绝动作并重新规划；不能重置截止时间。
- `SubmitAmbiguous`、窗口已关闭、未发送、候选耗尽或截止时间到达都必须停止旧窗口追加动作。
- `stage_open + qualified=false` 或 `NOT_QUALIFIED` 是参赛者正常淘汰，不等同于赛事 `finished/closed/void`。
- `stage_crashed` 关闭旧场次任务并标记作废尝试；新阶段和决赛加赛必须发现新的 `game_id`。
- `stage_attempt_id` 由应用生命周期在每次实际运行尝试开始时生成，用于审计；它不是官方字段，也不得由官方适配器猜测。
- 组委会推进阶段不算人工介入 Bot；我方程序不得要求人工选牌、确认到位、重启或继续流程。

## 验收标准

- Fake 会话覆盖报名、到位、多阶段、淘汰、候补、空窗、阶段重赛和决赛新增场次。
- 同一窗口 409 后可选择下一候选；模糊结果绝不追加；刷新不延长预算。
- 单场任务崩溃不取消同身份其他场次，单身份崩溃不要求测试启动器取消其他身份。
- GET 超时/5xx/429 有界恢复，401 和不兼容指南进入明确参赛者终态。
- 每次 POST 前有 `SUBMISSION_INTENT`，返回后有结果记录；审计失败不阻塞动作但运行标记 `audit_degraded`。
- 长轮询可在阶段切换和退出时及时取消，无任务、连接池或文件句柄泄漏。

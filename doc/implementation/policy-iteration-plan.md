## 1. 决定与范围

先冻结现有基线，再交付 V1 可靠排序、V2 可比牌效、V3 有限调参。V1/V2 现在即可实现，完整桌赛效果验证和 V3 调参等待模拟、评估模块通过验收。候选合入不自动替换线上稳定策略。

不能只改 `policy/evaluation.py`：它负责单次决策评分，`offline/evaluate.py` 才是比较策略效果的评估模块。过牌缺失的牌效由 `hangma` 补齐；排序、版本装配和真实耗时测试也需要修改。`BotPolicy.choose(DecisionRequest, DecisionBudget)`、观察类型和审计/模拟文件格式不扩展。

本轮提高启发式策略（`HeuristicPolicy`，没有模型也能独立完成比赛的策略）。紧急保底策略（`SafeFallbackPolicy`，计算失败时立即给出紧急动作）继续独立存在，不依赖新评分。

| 交付 | 核心内容 | 依赖 | 完成后可以声称什么 |
| --- | --- | --- | --- |
| V0 冻结基线 | 固定现有行为、完整权重、决策样例 | 无 | 比较对象可复现 |
| V1 可靠排序 | 合法胡牌优先；未知事实不占便宜；真实预算测试 | V0 | 已知排序故障修复，尚未证明桌赛表现提高 |
| V2 可比牌效 | Pass 当前等待牌效与吃碰后等待牌效统一比较 | V1；主审安排规则文件修改窗口 | 牌效比较基准一致，尚非真实行动价值估计 |
| V3 有限调参 | 六个现有参数变体，最多选一个独立验证 | V2；模拟和评估验收 | 只有完整桌赛实验支持时，才声称相应指标提高 |

本轮不加入搜索、他家手牌推断、摸牌概率模型、主动弃胡、复杂财神特殊链优化或赛事晋级效用。它们不属于这三个版本的完成条件。

## 2. 当前依据

以下区分源码事实、局部复现与工程建议，不是完整桌赛强度结论。

- 已复现：将原本排第 14、得分 -378 的 `discard:3b` 的 facts 单独替换为分析失败后，它以 0 分排到第一；原第一名得分 -267。源码对失败牌效给 0、对已知向听给负分，未知因此可能占便宜。
- 已复现：真实规则生成的一例中，Pass 得分 0，碰后向听为 1 的 Peng 得分 -95。Pass 没有向听和有效牌项，比较基准不同；这不证明该具体动作一定应该碰。
- 源码事实：立即胡靠固定加 1000 参与总分排序；权重无有限数值检查。可胡立即胡是本轮策略选择，不是官方强制胡牌规则。
- 源码事实：现有 benchmark 在开始计时前完成规则分析，且给出 `+0.9/+1.8/+2.7` 秒预算，不能证明完整本地决策链满足 1 秒窗口。
- 边界：有效牌的 `remaining_estimate` 包括牌墙和他家手牌中的未见牌，不能直接当成真实可摸张数或概率。固定杠加分、鸣牌惩罚、熟张和名次调整均还需要效果证据。

原规划引用的 [Suphx 原论文](https://arxiv.org/abs/2003.13590)用于研究方向参考，不是杭麻规则依据，也不能证明本项目某组权重有效。本轮优先处理已有反例与可比较事实，不照搬日麻防守或末局弃胡条件。

## 3. V0：冻结真正不变的比较对象

先建立少量版本预设和固定决策集，避免新版规则事实悄悄改变旧策略。

1. 保留原策略名 `weighted_heuristic`、原类 `WeightedHeuristicPolicy` 和 `weighted_heuristic.py/evaluation.py/weights.py`，不改名、不替换默认工厂；`claim_if_legal` 与 `safe_fallback` 源码也不改。
2. 基线指纹、完整默认权重与固定输入信息见 `baselines/heuristic-v0.json`。`tests/fixtures/policy/v0-decisions.jsonl` 保存八个完整观察/候选事实/计划案例；回归读取记录事实，不随当前规则重算。
3. V1 使用独立 `heuristic_v1.py/evaluation_v1.py/weights_v1.py`，公开类为 `ReliableHeuristicPolicyV1`，配置名 `weighted_heuristic_v1`；数值校验只影响 V1。允许有限代码重复以隔离历史行为，不使用一个不断增加版本分支的公共评分函数，也不新增 profiles 模块。
4. V1 已明确不消费未来新增的 Pass 等待牌效。V0 当前保持原始源码；V2 开工时，须另做显式旧事实适配和回归以维持 V0 在新版事实环境下的比较口径，不能悄悄修改冻结源码或混淆 recorded_request/recomputed_rules。
5. 当前固定版本名和完整默认权重清单可用于审计/实验配置；可调权重实验须额外记录完整权重。policy 不写文件，也不另造审计格式。

固定集验证旧版动作顺序和数值评分不变，覆盖所有动作族、两种已兼容手牌形态、抓打圈、缺失事实和已拒候选。V0 保留已知缺陷只为离线比较，不代表推荐部署这些缺陷。

### 3.1 冻结与线上验证的实际部署

冻结保存两件东西：可回退的完整代码提交及依赖/配置版本，以及可在共同运行框架中选择的旧策略行为预设。分支会移动，不能只记录分支名；实验记录精确提交、完整权重、规则语义版本和环境信息。Token 原文不进入实验清单。

开发使用隔离分支/worktree；联合验证使用一个已验收、固定提交的运行目录，包含旧/新策略预设，四个独立进程各选一个预设和一个 Token。共用相同 adapter/rule/application 版本，保持连接池、限速器、状态与审计目录按身份隔离。运行中不在该目录拉代码、改文件或安装依赖，同一 Token 同时只由一个进程持有。

首批测试房间使用一个候选身份、三个稳定策略身份；完成整桌比赛后，在后续完整比赛中轮换候选身份，并记录平台实际分配的座位。slot 标签和 Token 不能被当成固定座位。该实验用于运行验收和行为诊断；同房四家手牌不同，身份轮换也不等于复用同牌山，不能单凭相互分差认定策略强度提升。

当前 `scripts/run_participant.py` 支持每身份独立配置 strategy；`scripts/run_test_room.py` 原先只有房间级统一 strategy。S0 已补齐房间启动器的身份级 strategy 覆盖：身份未指定时继承房间默认，指定时传给现有单身份入口；同步策略名称校验和启动器测试，旧配置保持可用。之后一个配置、一次启动就能完成四身份混合策略验证，不需要日常维护四份独立启动流程。混合配置示例见 [policy-v0-v1-room.json](./examples/policy-v0-v1-room.json)，使用前填入实际房间信息并通过环境变量提供 Token。

### 3.2 后续版本管理：按配置选择，不按分支部署

分支/worktree 只隔离正在开发的工作，完成集成后可以收回；不为每个策略版本永久维护一个分支。共同运行版本通常只需保留当前稳定策略、一个待比较候选，以及独立紧急保底。历史发布由精确提交/标签、完整配置和依赖版本归档，需要复查时再恢复；不要求所有历史版本永久兼容最新运行框架。

参数变化新增一个不可变预设即可，复用同一评分实现；算法变化修改或增加 policy 内部实现，通过已有 `BotPolicy.choose()` 装配。未来模型策略也使用这条接缝，不新增通用插件系统。V0/V1/V2 是本轮行为修订标识，不是三个长期开发分支；稳定版本晋级后可从日常运行名单移除旧候选，保留归档证据。

策略在进程启动时固定，一次完整桌赛不更换。已有预设之间的实验只改配置；引入新算法代码仍需测试、集成和部署新固定提交。换版在完整桌赛结束后的实验批次边界进行，不实现局中热更新。

## 4. V1：可靠排序，不调打牌偏好

V1 不改变规则事实或牌效权重，修复“评分失效导致选择失真”。

### 4.1 排序算法

`evaluation.py` 的内部结果增加优先级信息，`weighted_heuristic.py` 使用完整排序键；不增加跨模块字段：

1. 规则合法候选中、未被拒绝的 `Hu` 最优先。非 Hu 动作不能仅因错误的 `WIN` facts 被提升为胡牌。
2. 其余候选中，完整、可评分的事实优先，层内沿用现有加权分数。V1 的合法 Pass 仍保留旧中性基线。
3. `facts=None`、`ANALYSIS_FAILED`、缺向听数值、候选事实自身为 `DEGRADED` 等进入未知层。保留候选和原因，但未知的 0 分不能压过可信的负分。
4. 非胡候选全部不可评分时，优先规则紧急候选；它缺失或已拒绝时，剩余候选按 `action_key` 排列。不得凭空制造动作。

总体 `RuleAnalysis.DEGRADED` 不等于每个候选事实失败；逐候选处理。杠的 `replacement_draw_unknown=True` 是已声明的估计边界，不等于分析异常，不据此降级所有杠。

排序键为“优先层、层内数值分降序、action_key”，全部未知时另使用上述紧急候选优先规则。`rank` 是执行顺序；`total_score` 仍为数值分项之和，不使用无穷大或巨大常数冒充分数。`reasons` 解释优先层与降级原因。

这是显式的策略排序语义变化：已同步规范中的“同层同分按 action_key”，审计和评估按 `rank` 展示/执行，不能自行只按总分重排。`DecisionPlan` 字段不变。

### 4.2 数值与时限

- `weights.py` 拒绝 NaN、无穷大和布尔值，默认权重不变。计算分项或总分若非有限，明确失败并由现有应用层保底，不能写出非法 JSON。
- 保留拒绝/重复过滤、紧急候选保留、截止时间检查和协程让出执行权；不增强 `safe_fallback.py` 的计算。
- 修正 benchmark，分别报告策略单独耗时及“紧急动作准备 → analyze → choose → validate”的本地耗时。通过现有 `BudgetPolicy.build()` 构造真实 1 秒响应和 3 秒出牌预算。
- 新进程测首次决策，同进程测重复决策；启动/导入单列。使用同一事件循环测 M 个并发窗口，记录机器、M、阶段耗时与预算余量。不先加缓存，不删除最终复核。

当前默认 1 秒窗口的增强、保底、最晚发送点为接收后 0.5/0.7/0.85 秒，所有阶段从同一接收基准计时，规则分析也占预算。最终复核后仍须留出发送时间；本地通过不能代替真实网络和测试房间验收。

### 4.3 验收

故障注入不再让失败候选压过可信候选；全部失败时紧急候选优先；调整其他有限权重不能压过合法胡；已拒胡不能重入。全部动作族、抓打圈、拒绝、异常、超时和 `claim_if_legal` 回归通过。冷/热及 M 并发预算报告齐全，超预算如实标为未通过，不放宽生产截止时间。

## 5. V2：统一过牌与吃碰的比较基准

本轮最值得实施的进攻决策修正，是比较“鸣牌后相对继续等待改善多少”。

### 5.1 规则只补一种事实

在 `hangma/candidate_facts.py` 的合法响应 Pass 分支调用已有等待状态分析，输入当前未改变的本人暗牌、已有副露数和同口径公开计数。不能把他家刚弃的牌加入本人手牌，不能扣不存在的后续弃牌，也不能猜未来摸牌。校验响应手牌形状；错误沿用 `ANALYSIS_FAILED + RuleIssue`。

返回已有 `CandidateFacts`：`HAND_PROGRESS`、真实分析所得向听/有效牌、`best_followup_discard=None`、`replacement_draw_unknown=False`。吃碰继续使用现有“鸣牌后最佳合法弃牌后的等待状态”。不新增字段，不改动作合法性、胡牌、结算或模拟推进。

单独提交并登记新的本地规则语义版本：这是候选分析变化，不是官方规则变化。旧 `NOT_APPLICABLE` 继续可读，历史记录不重写。

### 5.2 策略计算

V2 对 Pass、Chi、Peng 使用相同牌效项：`-100 × 向听 + 有效牌剩余估计之和`。保留财神项、碰惩罚 6、吃惩罚 10；杠和弃牌沿用 V1，不同时调参。

只看牌效与鸣牌惩罚、共同项抵消后的受控例子：

| 规则事实 | Pass 分数 | Peng 分数 | 应有排序 |
| --- | --- | --- | --- |
| Pass 向听 2/有效牌 20；Peng 向听 1/有效牌 15 | -180 | -91 | Peng 在前 |
| 两者均向听 1/有效牌 15 | -85 | -91 | Pass 在前 |
| 同向听，Peng 比 Pass 多 10 张有效牌估计 | 基线 | 基线 + 4 | Peng 在前 |

这些是评分验收，不是人工宣称真实最优动作。另用真实观察经 `HangmaRules.analyze()` 覆盖吃碰改善、不改善、恶化和有效牌耗尽的集成案例。

V2 若收到旧版/失败的 Pass 事实，标明“缺可比等待基线”；合法未拒的 Pass 优先作为响应退路，无可用 Pass 时沿用 V1 降级。历史请求可检查兼容退路；测试新事实需用评估器的 `recomputed_rules`，保留原/新差异，不能冒充历史原请求实验。

吃碰 facts 的最佳后续弃牌按规则牌效键选取，实际下次策略仍可能受财神/风险项影响。这只是牌效代理，不是完整续打价值；本版不扩展全部后续弃牌事实。

### 5.3 验收

同观察的合法动作集合、紧急动作和结算不变；仅登记的 Pass 事实改变。公开牌不多计，手牌形态兼容，异常不造数值。V0/V1 在新事实下仍保留旧评分；V2 兼容退路可解释。吃碰两族都有应鸣/应过测试，并重新通过 V1 时限门禁。

## 6. V3：有限参数试验

只在 V2 和模拟/评估验收后执行，以 V2 为共同对照，每个变体只改一组参数：

| 变体 | 唯一改动 | 检验问题 |
| --- | --- | --- |
| C1 | `claim_risk_peng=3, claim_risk_chi=5` | 鸣牌惩罚是否过重 |
| C2 | `claim_risk_peng=12, claim_risk_chi=20` | 鸣牌是否过于积极 |
| C3 | `gang_bonus=0` | 固定杠奖励是否有害 |
| C4 | `gang_bonus=20` | 较小杠奖励是否更稳 |
| C5 | `feed_risk=0` | 现有副露邻近风险近似是否有用 |
| C6 | `style_adjust=0` | 当前桌内名次微调是否有用 |

连同 V2 共七组，不做笛卡尔积。C5 只验证风险分值，不同时证明“熟张安全”假设。财神保留、向听、有效牌权重和熟张分支暂不变；不用未消费的 `flexibility` 制造优化项。

调参集最多选一个变体做独立留出验证，不直接拼接几个分别看似有效的改动。没有清晰改善就保留 V2；V3 可以以“无参数变更”结案。

规则事实提交由主审与模拟线排定窗口，避免并改同一文件。策略线不修改其 `progression.py`，也不改 `offline/`、`simulation/`、官方适配器、审计 codec 或 `application/decision_loop.py`。评估线消费策略预设/实验配置，审计线记录既有字段内的版本和原因。若时限测试暴露其他模块瓶颈，再提具体独立修复。

## 8. 评估、发布与停止条件

先过固定决策集，再做完整桌赛（`TableMatch`，按实际 `config.Rounds` 完成的同桌比赛）的复式评估（`Duplicate Evaluation`，同牌山并换座位）。动作变化率、单局胡牌率不替代完整桌赛表现。

V1、V2 均须比较后决定是否发布，不预设比赛表现必然改善。顺序是 V1 对 V0；V1 通过验收后，V2 对固定的 V1，必要时另报告 V2 对 V0。若 V1 尚未发布，它只能标为已验收的实验对照，线上稳定版本仍另行记录；不能把未验收候选自动当基线。无需安排 V0/V1/V2 三版同桌，也不必为了每个候选单独参加一次官方测试赛事。

一次受控比较执行两组独立完整桌赛：例如 A 组为 V0 加三个固定对手，B 组为 V1 加相同三个固定对手，使用相同初始牌山安排/随机源版本和座位；再轮换待测座位。只替换待测策略，后续因动作不同而产生不同牌局发展是允许的。比较 V2 时同理替换对照。不能要求两条策略轨迹之后一直摸到相同的牌，也不能只拿同一桌不同手牌的两个身份直接做配对效果结论。

模拟器尚未通过验收时，先完成固定决策比较、故障回归、预算测试和测试房间混合策略验证；这能交付候选及运行证据，不能证明完整桌赛效果提高。官方测试赛事负责完整赛事生命周期发布门禁，自动匹配负责外部实战观察，都不能代替上述受控策略比较。

1. 模拟规则一致性及评估完整性通过后，先用 20 个独立 scenario 根组检查流水线和吞吐，不用这批选参数。
2. 首批建议 200 个调参根组、1,000 个独立留出根组，每组四座位轮换，候选和对照分别占相同座位，对手/规则固定。这是工程规模，不保证统计功效。时间不足可根据吞吐在看效果前缩小并冻结样本数；V1/V2/V3 的正式验证使用各自独立留出组，不复用留出集挑版本。
3. 预声明主指标为配对桌内积分差，报告按 scenario 聚类的 95% 置信区间；同时报告桌赛第一率、胡牌率、鸣牌/杠率、异常、保底和耗时。换座位及单个决策不当作独立样本。
4. V1 属可靠性修复：必须消除已知故障、通过预算/恢复门禁，并报告完整桌赛指标及区间检查行为退步；不要求先证明桌内积分显著增加。若使用“不劣于基线”作为发布依据，须在实验前声明可接受退步界限，按区间判断；不能把“差异不显著”当作不劣证明。V2/V3 属强度候选：主指标区间下界大于 0 才支持桌赛积分改善；跨 0 就写改善证据不足，不自动上线。其他指标明确退步须单列解释。桌赛积分改善不等于赛事晋级率改善。
5. 本地通过后做测试房间 M>1 及实际部署 M 验收，自动匹配用于外部对手和运行问题发现，其非受控分差不替代复式评估。发布仍遵守目标赛事格式、运行可靠性和人工审核门禁。

每版交付代码提交、完整预设/规则版本、固定案例检查、评分差异和耗时报告。比赛产物复用评估线的 `manifest.json + decisions.jsonl + results.jsonl + report.json + report.md`；跨机器传递实验配置、报告和输入内容哈希，不依赖另一台机器默认参数或共享运行中数据库。

S0/S1 候选已实现，测试与限制见 [V1 实施验收记录](./reviews/policy-v1-implementation-2026-09-05.md)；随后才进入 S2/S3；模拟和评估就绪后做 S4。V2 稳定且有限调参没有确切改进，本轮即结束，把研发精力转回模型与训练数据。

## 9. 与原训练规划的衔接

本次收敛不取消两个模型的长期方向，但不为它们提前增加线上接缝。候选结果模型仍需模拟展开或可靠终局标签，实际动作记录不等于所有候选的反事实标签；阶段续局模型仍需真实阶段格式、对手分布与排名结果，桌赛模拟器不自动具备阶段能力。后续创建 learning 时统一训练/推理编码，按 split_group_id 分离数据并记录规则、策略、对手池、采样器、校准和随机种子版本。

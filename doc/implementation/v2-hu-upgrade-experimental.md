# V2等胡实验策略：主线自由赛接入

`v2_hu_upgrade_v1` 已作为显式选用的实验策略接入主线，支持 `auto_match` 和 `test_room`。默认策略、常用模板及冻结V2均保持原样；正式赛事与测试赛事入口仍拒绝该枚举。用户于2026-09-09要求用于自由赛试验，这不等于通过稳定版替换门槛。

## 1. 使用与实际生效范围

在既有自由赛私有配置里仅修改策略项：

```json
{"strategy": "v2_hu_upgrade_v1"}
```

上述为配置片段。继续使用 `scripts/run_auto_match.py --config <原配置>`，保留现有Token来源、M/Rounds声明、审计及连续运行设置。无需新Token；本次代码合入没有启动房间，也没有修改正在使用的配置或终止现有进程。新的策略选择在下次进程启动时生效。

等胡增强只在平台实际配置为 **BaseScore=1、`YouCaiBiKao=false`、`hangma-mvp-v10-public-counts`** 时启用。其他配置下，自由赛继续使用该配置的真实规则，关闭可选分值事实，策略完整回到V2，不退出已经匹配入席的房间。测试房保留严格拒绝不适用配置的行为，便于诊断。

自由赛manifest同时记录实际 `base_score/you_cai_bi_kao/ruleset_version`、配置选择的 `policy_version`、风险参数版本以及真正启用的 `value_analysis_limits`。`value_analysis_disabled_reason=uncalibrated_rule_config` 表示规则不在校准范围；`not_requested` 表示普通策略没有请求分值；为空表示分值已按声明启用。即使启用，单次请求仍可能因事实缺失、预算或风险分组不覆盖而沿用V2。

`policy_weights.upgrade_weight=1` 是请求的算法参数，不应单独用它判断增强生效；应结合实际规则、分值启用字段和逐决策审计。规则不适用时 `policy_version` 仍记录用户配置的枚举，避免混淆试验身份。

## 2. 相对V2改变什么

普通弃牌、吃碰和杠的基础评分仍来自冻结V2。只增加两类选择：

- 当前能够胡，且规则完整证明某个弃牌后下一次普通自摸必定爆头、最低净分更高时，按风险校准比较是否等一次摸牌。先保留合法胡和紧急动作，不预支多次飘的收益。
- 响应窗口已经具有完整爆头等待证明时，优先合法过牌，保持下一次自摸估值依赖的手牌。

风险表 `hu-upgrade-risk-v2-v10` 来自V2模拟对手池：低威胁组中，余牌40–63用生存估计0.83，至少64用0.92；失败支付估计为当前胡分的0.10倍。选择条件为 `p×下一摸最低净分−0.10×当前胡分 > 1.10×当前胡分`。余牌包含保留区；其他风险组不主动弃胡升级。这不是实际自由赛对手的概率保证。

独立确认128根、四次换座、双方合计1,024个完整八单局桌赛中，每桌净分差+4.3359375，95%按根聚类区间[+1.9140625,+7.3984375]。未达到事先要求的至少+10分，故仍标为实验策略。自由赛数据用于补充真实对手证据，不能直接与不同牌山的旧V2总分相减作为因果提升。

原始紧凑证据：[风险表](../../review/v2-hu-upgrade-v10-2026-09-09/risk-table.json)、[确认报告](../../review/v2-hu-upgrade-v10-2026-09-09/confirmation/report.json)、[门槛核验](../../review/v2-hu-upgrade-v10-2026-09-09/verification/final.json)。完整实验产物仍保留在 `codex/v2-hu-upgrade` 的1305b2c2及后续历史中；本次没有将数千个历史实验文件整批合入主线。

## 3. 已实现的一次摸牌事实契约

本次带入候选所必需的已有规则能力：`HangmaRules.analyze(observation, *, value_limits=None)`。缺省保持普通规则路径，非空参数为 `ValueAnalysisLimits(max_expansions=2048, max_routes_per_candidate=128)`；固定工作量不访问时钟，不延长动作原始截止时间。

`RuleCandidate.value_facts` 默认 `None`，由规则模块唯一生产。类型为 `CandidateValueFacts`：

| 字段 | 语义 |
| --- | --- |
| `immediate_settlement` | 当前合法胡的确定结算；非当前胡为空。四家分差按座位0—3排列 |
| `routes` | 下一次摸牌直接成胡的互斥进张分组，不是完整单局价值或概率 |
| `coverage` | `complete/partial/unavailable`，仅针对一次摸牌范围的完整性 |
| `issues` | 截断、缺失证据或失败原因；非完整结果必须带原因 |

每条 `ValueRoute` 保存条件结算、向听0、有效进张及未见张数、吃碰后的指定弃牌、条件与 `support=conditional_witness`。`ValueConditions` 保存普通/补牌来源、摸前本人暗牌、面子数、链次数、链内飘白及爆头证明。未见张数包含他家暗牌的可能，不代表真实牌墙数；不同吃碰后弃牌互斥，不能相加。未来牌型、爆头、开关过滤和结算都复用现有规则源，没有第二套规则算法。

`audit_codec` 对新增分值可选读写；旧记录缺字段仍还原为None。`BotPolicy.choose`、`DecisionRequest`、`DecisionPlan`及四个外部端口保持不变。

## 4. 两个运行入口的接线与降级

`ParticipantRuntime` 与 `RuntimeServices` 增加可选 `value_limits`，组合根仅为候选显式开启。动作循环先取得独立紧急动作，再在原增强截止前请求分值；409后的刷新不会重置预算，迟到窗口不再启动增强。分值失败保持合法候选，策略失败或截止仍走已有完整保底。

自由赛有独立 `AutoMatchRuntime`，本次增加 `value_limits` 与可选 `value_rules_scope: RuleConfig`。后者只描述组合根允许使用分值的配置范围，不替代平台实际规则。初始化取得实际配置后比较，命中才将分值限额传入 `RuntimeServices`；未命中则传None。声明范围但未声明限额在构造期报错，避免无意义的配置。

阶段、并发、限频、HTTP、动作门和终局收尾继续复用原实现，不把等胡判断放入适配器。选择候选不会改变M声明；一个身份仍最多管理平台实际配置M个场次。源代码不存在两摸离线原型或新的线上搜索。

## 5. 验证与边界

合入检查覆盖自由赛和测试房各10个同时到达窗口的真实规则/策略/审计接线；开启配置出现预期等胡弃牌，普通V2没有分值额外成本。自由赛对四类不适用配置完整运行到终局、没有分值事实，决策与实际规则下的V2一致。另覆盖官方金例、C/Python降级、候选失败、原始截止、409重试、限频及收尾回归。

测试使用替身网络，不消耗真实房间。原始规则证据包括官方v23计算器记录，仍按v10公开计数和v26动作规则工作；本次未更改C/Python牌型数学，也没有声称重新请求在线官方计算器。验证结果与来源见[合入记录](../../review/hu-upgrade-main-2026-09-09/README.md)。

# V0 冻结与 V1 实施验收记录

> 2026-09-05；当前是本地实现与验收，未切换默认策略，未启动官方房间，未证明完整桌赛表现提高。工作区中的审计、模拟、评估和规则推进并行文件未修改。

## 1. 交付与兼容

V0 保留现有 `weighted_heuristic` 名称和 `WeightedHeuristicPolicy` 类。原入口、评分、权重、claim_if_legal、safe_fallback 五个文件的 SHA-256 均与冻结时一致，见 [基线清单](../baselines/heuristic-v0.json)。清单保存精确源码提交、完整默认权重、八个固定决策输入的哈希和捕获环境。

V1 配置名为 `weighted_heuristic_v1`，类为 `ReliableHeuristicPolicyV1`；独立入口、评分和权重文件分别为 `heuristic_v1.py`、`evaluation_v1.py`、`weights_v1.py`。不创建版本分支框架，不修改 V0 文件，不修改规则 Pass 事实。默认策略仍为 V0。

`BotPolicy.choose()` 和全部数据字段保持兼容，只有 rank/total_score 的解释注释同步：V1 按优先层执行，跨层分数可能不单调；消费者必须保持 rank。已登记在接口协议 §4.2 与 parallel-v1，相关应用测试证明不会按总分重新排序。

## 2. V1 行为

1. 已在规则合法候选中且未被拒绝的 Hu 优先，其他权重不能压过它。非 Hu 的异常 WIN 事实进入未知层。
2. 可信候选沿用 V0 默认数值偏好，未知候选排在其后；全部未知时优先尚可用的规则紧急候选。整体规则降级不抹去每个候选自身的完整事实。
3. V1 的 Pass 保持原中性基线，不提前消费 V2 的等待牌效；分析失败或缺失的 Pass 不冒充可信中性事实。杠补牌未知标记本身不导致分析失败降级。
4. V1 权重构造拒绝非有限/非数值参数；计算溢出明确失败，现有应用层转紧急保底。V0 权重类不受影响。
5. 候选去重、动作键复核、拒绝排除、确定性、截止时间让出与异常取消保留；评分完成和计划返回前补充截止检查。

## 3. 决策证据

固定历史输入回归覆盖普通弃牌、手牌已含摸牌、吃/碰响应、七对胡、暗杠、抓打圈和财神。V0 完整计划逐项一致；V1 在这八个完整事实案例中的动作顺序和数值分数与 V0 相同，理由文本反映新层级。回归直接读取当时的候选事实，不通过当前规则重算。

故障注入复现：只将真实分析中的 `discard:3b` 事实改为 ANALYSIS_FAILED，V0 首选变为该牌，V1 首选仍为 `discard:1w`，失败候选移到末尾。候选集合不变。此证据证明失效事实的排序问题得到修复，不证明该具体出牌是牌局最优。

测试还覆盖：极端但有限权重下胡优先、伪 WIN、未知分类、负/空/非整数向听、部分降级、全未知、已拒紧急候选、非有限配置与溢出、计划取消，以及应用层实际提交遵守 rank、真实 V1 异常触发保底。

## 4. 本地时限证据

环境：macOS arm64，Python 3.11.15。使用实时时钟和生产 `BudgetPolicy.build()`，计时包括 emergency → analyze → choose → validate，均从窗口接收基准开始；M 个窗口运行在同一事件循环。进程启动/导入不计入动作处理耗时，另行记录。

一次独立基准运行的 V1 结果如下（毫秒，均为本地核心调用）：

| 场景 | M | 从接收到复核完成的最差耗时 | 最晚发送点前余量 |
| --- | --- | --- | --- |
| 固定出牌样例，热路径 | 1 | 3.8 | 2546.2 |
| 固定碰响应样例，热路径 | 1 | 2.0 | 848.0 |
| 固定出牌样例，并发热路径 | 10 | 32.6 | 2517.4 |
| 固定碰响应样例，并发热路径 | 10 | 18.7 | 831.3 |
| 新进程首次出牌 | 1 | 48.7 | 2501.3 |
| 新进程首次碰响应 | 1 | 18.7 | 831.3 |
| 新进程十组不同手牌同时出牌 | 10 | 846.9 | 1703.1 |

各窗口 choose 均在增强截止时间之前完成，最终复核也在最晚发送之前。V0 使用相同基准独立运行，固定样例未显示明显量级差异；这些小规模耗时不用于声明 V1 更快。

限制：固定样例和十组不同手牌不是任意复杂牌型的最坏界限；未覆盖所有长短窗口混合到达、真实网络、SSE、审计磁盘和官方调度。仍需在实际部署机器及实际 M 下进行测试房间验收。没有模拟器效果报告、桌赛积分置信区间或赛事晋级证据。

## 5. 运行方法

[混合房间配置示例](../examples/policy-v0-v1-room.json)默认 V0，仅身份 A 覆盖为 V1。身份未指定 strategy 时继承房间策略，旧配置仍可用；四个身份继续使用隔离子进程、连接和审计目录，Token 通过原环境变量通道传递。房间启动日志显示每身份实际策略。

复制示例到私有运行配置，填写真实平台地址/测试房间 ID，按原配置设置所需内网 TLS 白名单并提供四个 Token 环境变量，再运行：

```bash
.venv/bin/python scripts/run_test_room.py --config YOUR_PRIVATE_ROOM_CONFIG.json
```

本次没有替用户启动比赛，也没有更改现有私有运行配置。对照实验更换策略在完整桌赛结束后进行；V1 是否发布按路线 §8 的可靠性及行为退步门禁决定。

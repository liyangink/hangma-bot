# VIP P2 条件状态与给定公开事件接口方案（待受控冻结）

日期：2026-09-30。**结论：P2 应在 `hangma` 内增加一个只消费本人暗牌与已见或明确给定公开事实的条件推进入口，并把它接到现有规则函数；当前实现尚未达到机械完成门。**本文只冻结拟议边界与实施顺序，不宣称已改动接口、通过测试或取得新的官方规则证据。首个目标配置限 `BaseScore=1`、`YouCaiBiKao=false`。

## 依据和边界

官方依据是[指南 v34 正文快照](../../doc/references/official-guide-v34-content.txt)（2026-09-15 抓取）的规则、动作窗口与 API 段，以及[规则证据表](../../src/hangma_bot/hangma/RULES_EVIDENCE.md)；v35 只有[版本记录复核](../freematch-deep-dive-20260925/OFFICIAL-GUIDE-V35-G266-RULE-DELTA-2026-09-29.md)（2026-09-29），没有取得全文，不能以 v35 补写规则。工程现状以[P2 机械矩阵](./P2-MECHANICAL-MATRIX.md)、`route_transition.py`、`progression.py`、`engine.py` 和 `public_tile_counts.py` 为准。[P1 接口契约](../../doc/implementation/interface-contracts.md#411-独立路线策略的-p1-研究接口2026-09-30)仅保证声明的一次本人普通摸牌条件边，不能据此认定正常响应和杠补已闭合。

玩家观察（`PlayerObservation`，官方快照与连续事件构成的本人依法可见状态）只作为**根输入**。条件路线状态（`ConditionalRouteState`，一条明示条件分支上的本人暗牌与公开事实）是内部研究值对象，绝不实例化、继承、序列化成新的 `PlayerObservation`。完整世界状态（`WorldState`，含他家暗牌与牌墙顺序的模拟状态）不能进入此入口。已发生的公开事实与研发给定的未来条件在类型和结果标签上分别保存；给定牌码表示“若发生”，不表示牌墙中有该牌，也不是摸到它的概率。未知对手手牌、未知响应选择和未公开结果保持未知。只有官方已给的 `seq` 才能写入官方序号字段。

当前 `route_transition.py` 的 `meld_count`、`my_peng_codes` 和 `catch_restricted` 足以支撑少数局部对拍，却不足以处理副露来源、牌河重叠、圈主接力和响应裁决。其吃碰根先移本人牌、杠根先转待补牌，在新版契约中应明确为**动作获裁决或执行成功之后的条件分支**；尚待裁决时仍保留未提交根，不把提议响应写成既成公开事实。

## 最小状态及不变量

状态按单局、单根分支不可变。下表是字段语义草案，字段名属提案，落码时由受控接口评审定名；外层四座向量均按座位 `0—3` 排列。`None` 只表示该字段的证据尚不足，不等于零、`False` 或空列表。

| 字段组 | 必须携带的事实及可空条件 | 校验与用途 |
| --- | --- | --- |
| 分支身份 | `game_id`、`round_no`、本人 `seat`、`dealer_seat`、`root_action_key`、`branch_path` 均非空；`ruleset_version`、规则配置和源码摘要绑定根分析 | 不同单局、根、规则身份不得混合；`branch_path` 是本地条件步骤标识，绝不充当官方 `seq`。 |

当前 P2 内部 `ConditionalRouteState` 已把根观察的 `dealer_seat` 固定传过本人摸牌、鸣牌预列和再杠条件状态；含本人座位的状态缺庄家直接拒绝。结算分析若调用方传入另一庄家也直接拒绝，不能让同一条件根算出两套四座净分。`ConditionalIdentity.ruleset_version` 现由根使用的 `RuleConfig` 写入并沿本地路径继承，给定本人摸牌或吃碰暂态若换用另一规则版本直接拒绝；旧手工构造的公开前缀可空，但不得通过这种前缀冒充已绑定的本人结算入口。源码摘要与完整规则配置身份仍属后续合同验收，不因庄家及规则版本落地就称整个身份行完成。
| 已见水位 | 根 `snapshot_seq` 非负；`consumed_seq` 可空，非空时不得小于快照序号；已见事件仅覆盖到已确认水位 | 快照为其水位内权威事实；有缺口、冲突、跨局或未知关键事件时停止该分支，不能继续套旧公开状态。 |
| 本人牌 | 仅本人 `concealed`、当前 `drawn_tile`（非本人摸牌动作窗为空）、完整本人 `PublicMeld`；本人手牌顺序按当前归一化规则保留 | `drawn_tile` 在摸牌动作窗必须有已见或给定来源；吃碰后未摸牌的弃牌暂态必须为空，故无胡候选。副露数、吃摊数、未升级碰牌码从具体副露派生，不存第二份可漂移计数。 |
| 公开牌 | 四座 `discards`、四座 `melds`、四座 `hand_counts`、最近弃牌及领取关联证据；`wall_remaining` 为官方口径**含保留区**的剩余张数，可空 | 本人副露与四座副露视图必须一致。牌河究竟留存被领取牌由实证决定，不能默认；缺墙余时不得用守恒等式推断移除口径。 |
| 窗口 | 条件阶段、`turn_seat`、有序且不重复的 `responding_seats`、待裁决弃牌、待补牌请求 | 阶段区分响应待裁决、吃碰后未摸弃牌、普通待摸、杠补待摸、本人摸牌决策和终局。当前本人合法动作须来自同次规则分析；对手给定动作只作为条件事实，不声称已验证其暗牌合法性。 |
| 本人规则态 | `baotou`、`chain_count` 非空；`chain_piao` 可空且非空时在 `0…chain_count`；本次摸牌来源为 `ordinary/replacement/unknown` | 链内飘白未知时不得精确结算；来源未知时不得按普通或杠补计算资格。杠后的待补请求必须记杠种及杠已获执行的证据。 |
| 抓打圈 | 活跃标记、圈主座位、开圈身份、证据来源；无圈时圈主为空，活跃而无法证明时圈主可空 | 本人受限结果从活跃与圈主派生，不复用旧 `catch_restricted` 布尔值。圈主未知则按既有保守限制并报输入证据缺口；未来弃白、关圈必须逐事件更新。 |
| 结算上下文 | 桌内 `scores` 仅在累计终点需要时携带，四座顺序 `0—3`；单次胡牌 `Settlement` 仍由现有结算模块给出 | 不把缺失积分补零；本地番数与四座积分增量的意义分开。 |

阶段和字段应做结构校验：待摸状态不能预填未来牌；待补牌必须有一条已执行杠的来源；响应阶段必须有触发弃牌与响应成员；本人摸牌动作窗必须有本人摸牌及明确普通/补牌来源；终局不得再展开动作。`wall_remaining <= 20` 不允许再给定普通摸牌；最后 20 张内禁杠沿用 `action_families`。规则配置与根分析不匹配、本人牌物理超过四张、本人副露和公开副露冲突，都属于机械或装配错误，不能压成“输入缺证据”。

## 给定公开事件和事件身份

建议入口语义为 `HangmaRules.advance_conditional(state, given_event) -> ConditionalTransition`，另以 `HangmaRules.analyze_conditional(state) -> ConditionalAnalysis` 取得当前所有合法动作和立即结算。这是 `hangma` 的**内部受控规则入口提案**，不扩展线上 `BotPolicy.choose`、HTTP 端口或 `PlayerObservation`。前一入口只推进一个已给定事件；后一入口对当前条件状态走同一合法动作、资格、手牌分解和结算实现。输入错误返回结构化 `RuleIssue` 与 `INPUT_EVIDENCE_GAP` 或 `MECHANICAL_GAP`；不把异常吞成空合法集合。分析工作上限截断继续单列 `SEARCH_TRUNCATED`。具体返回类型需在实施切片中冻结。

| 事件字段 | 语义和非空要求 | 约束 |
| --- | --- | --- |
| `provenance` | `observed` 表示已收到的公开事件；`assumed` 表示条件假设，必填 | 输出一直保留来源，不能把条件假设称为官方验证。 |
| `identity` | 已见事件用官方 `(game_id, round_no, seq)`；假设事件用 `(root_action_key, branch_path, step_index)`，其中 `step_index` 从 1 严格递增 | 假设事件的 `official_seq` 必须为空；本地序号不得注入 `PublicEvent.seq`、快照或 `consumed_seq`。同身份不同内容是冲突，不择一继续。 |
| `kind`、`seat`、`tile/tiles` | 已见 `tile_discarded`、`chi`、`peng`、`gang`、`pass`、本人 `tile_drawn` 沿用规范事件名；假设的整窗 `response_resolution` 是本地条件类型，不冒充官方事件；座位及牌字段按种类必填 | 他家普通 `tile_drawn` 只给摸牌发生与座位，牌值为空；不能给假设事件附他家隐藏摸牌值。本人给定摸牌需明确牌码。 |
| `window_ref` | 响应事件指向同一触发弃牌及 `response_peng` 或 `response_chi`；非响应事件可空 | 不能把后来的响应接到另一张弃牌，或把吃抢在碰窗之前。 |
| `claim` | 吃、碰、明杠给定裁决需明确是否获裁决；获裁决时供牌座位、被领牌码和副露牌形必填 | “我提交碰”不等于“碰已生效”。拒绝、过牌或他人优先生效后，本人暗牌不移。补杠只升级原碰，不再次领取弃牌。 |
| `draw_source` | 本人 `tile_drawn` 必为普通或杠补；杠补还要关联已执行的杠种及待补请求 | 官方 `gang_replenish` 已见时沿用其值；无可靠来源的旧观察保持未知，不默认普通摸牌。庄家发牌直抽没有摸牌事件，须作为有根快照依据的特殊起点，不能创造事件。 |
| `post_public_view` | 只有在牌河保留/移除口径无法由已有事实推出时，才显式给定受影响的牌河与副露后态及其来源 | 它是条件公开事实，不是权威快照。给定视图与事件、物理上限或已见权威事实冲突时拒绝该边。 |

已见事件去重后必须满足官方 `seq` 严格递增；重复同内容可去重，不同内容冲突即停。快照后的事件必须连续；官方缺口按现有适配器/规则恢复边界处理，不能由条件事件补号。假设的 `response_resolution` 一步承载该窗口完整选择集合与确定裁决，缺成员选择则保持待裁决，不生成部分裁决事件；已见官方事件仍逐条按其实际公开序处理。假设事件只在自己的 `branch_path` 内按 `step_index` 顺序前进，其与未来官方 `seq` 没有大小关系；后来拿到真实轨迹时重新以官方快照和事件建根，再对拍条件结果。跨单局必须以新权威快照建根，尤其不能把上一局 `settled` 手牌当作新局起手牌。

## 公开牌、响应和抓打圈的同源处理

公开牌计数须从同一张公开状态与事件证据计算。`public_tile_counts.count_public_tiles(PlayerObservation)` 现有实现把牌河、副露、手牌张数、墙余与连续事件配对放在一起，且兼容“被鸣牌留河”和“被鸣牌移河”两种实测口径。实施时应提取一个只接受**公开牌视图和证据**的纯计算核心，让现有观察入口与条件入口共同调用；不能为了调用旧签名构造伪 `PlayerObservation`。只有证明被领的同一物理牌仍在供牌者河中才扣一次重叠；守恒读数为零时不扣，证据不足时保守不扣并暴露容量证据状态，矛盾时受影响牌码为未知，超过四张不得截为四。公开未见容量还要扣本人暗牌和当前摸牌**恰好一次**，单位为张；它不是墙内概率。暗杠公开四张、明杠领取一张、补杠继承原碰那一次领取，均不能重复计牌。容量计算无法闭合时不输出伪精确路线边。

响应裁决应复用 `progression.resolve` 已体现的窗口顺序与裁决规则，但不能为此造一个含他家暗牌的 `ProgressionState`。最小重构是从 `progression` 抽取仅依赖公开窗口、弃牌、响应成员、抓打圈和**完整给定选择集合**的纯裁决核心：模拟推进和条件推进共用它；模拟器继续单独持有牌墙、他家暗牌与物理移牌。碰/明杠窗先于吃窗，碰窗全部过后才可能开下家吃窗；明示两家及以上同时碰/明杠时沿用现有 `blocked`，不得擅定先到先得。缺少某成员选择时保持待裁决，不能推断全过。若给定的是已见官方裁决事件，则按实际公开顺序接受其事实，不回推未公开的对手选择。本人根动作仍由同次 `RuleCandidate` 验证；吃碰获裁决后，全部合法后续弃牌继续取 `CandidateFacts.followup_branches`，且“鸣牌后、未摸牌”无胡候选。

抓打圈活跃与圈主由已见快照圈主字段和连续公开事件，或条件分支里的给定公开弃牌，走 `hangma.catch_play`/`progression` 同一规则：最新弃白者接管，同座续白也更新开圈身份；仅当前圈主随后弃非白关圈；摸牌与杠不关圈。本人受限由当前圈主是否本人派生；圈内非白弃牌的碰/明杠响应仅给圈主，圈主是下家才可吃，白本身不可吃碰明杠。这里依[规则证据表的 v26 修订](../../src/hangma_bot/hangma/RULES_EVIDENCE.md#2026-09-09-当前圈主规则官方-v26指南-v27)和指南 v34；若输入缺圈主或事件断裂，保留未知并降级，不拿旧限制继续展开。抓打圈公开权限与本人的爆头、飘杠链分别推进，不能互相代替。

三类杠均须由同次合法候选进入待补牌，并复用 `progression.chain_after_action`、`baotou_after_action` 与 `baotou_after_draw`：暗杠从本人暗牌取四张并新增暗杠副露；明杠获响应裁决后取三张、领取弃牌并新增明杠副露；补杠取第四张并原位升级碰副露，保留原供牌者。只有与待补请求一致的给定本人 `tile_drawn` 才能进入下一个摸牌动作窗，届时用同一 `action_families`、有财资格、`hand_analysis` 和 `settlement` 计算胡、弃、再杠及四座结算。当前 `route_transition.analyze_given_self_draw` 的直接调用组合可作为对拍参照，正式入口须纳入与 `HangmaRules.analyze` 同源的过滤和候选事实，不能只因生成了 `Hu` 就跳过资格判断。

## 受控变更范围、验证和切片

**此文不修改受控接口。** 真正落码时，先在[接口契约](../../doc/implementation/interface-contracts.md)登记新状态/事件/结果、空值、错误、版本与根候选身份；若公开入口扩到 `HangmaRules`，同步 `hangma/interface.py`、`engine.py`、所有调用方和契约测试。模块和数据流改变时同步[架构图](../../doc/architecture.md)、主技术方案及[术语表](../../UBIQUITOUS_LANGUAGE.md)的歧义项。`kernel.PlayerObservation`、四个 MVP 外部端口、线上 `DecisionRequest` 和策略 `choose` 暂无扩展需求；公开牌共用核心留在 `hangma`，不把规则移到 `simulation` 或 `policy`。P1 默认行为与旧审计不改写。

按下列顺序形成可审查的小切片，每片只在前一片的契约和测试稳定后接下一片：

1. **状态与身份。** 冻结条件状态、给定事件来源及本地/官方双身份，根从同次 `RuleAnalysis.legal_candidates` 一一建立。测试同一根多分支、事件重复/冲突/缺口、跨局、未知链/摸牌来源和不伪造观察/序号。
2. **公开牌核心。** 抽出已有 `public_tile_counts` 的公开视图计算，原观察入口逐样本不变；条件入口覆盖留河、移河、证据不足、同码重复弃牌、吃的领取牌、明杠与补杠继承重叠、守恒冲突及每码四张上限。比较 34 牌码结果，不以一次成功计数推断真实牌墙分布。
3. **公开裁决与圈主。** 共享 `progression` 的公开裁决/圈主转移；测碰窗→吃窗→摸牌、全部过、单人获裁决、多人冲突 `blocked`、未知选择停留、弃白接力、圈主非白关圈及圈内响应身份。以官方 v26/v27 金例和已有夹具核对；假设组合明确标条件，不称官方实测。
4. **本人完整正常转移。** 把弃牌、过、吃碰获裁决及其全部弃牌分支、三类杠、普通摸牌、杠补、再杠、当前胡和终局接到同一条件入口。覆盖连续杠、飘/断链、最后一摸、四白/豪华七对/普通型交互；每个给定动作的合法集合、资格与即时结算同生产规则对拍，缺证据与机械错误分开计数。
5. **机械门复核。** 按[P2 矩阵](./P2-MECHANICAL-MATRIX.md)逐格记录分母、正容量条件牌码、给定公开事件序列、完整率与未闭原因；在固定配置下任何正常格仍有 `MECHANICAL_GAP`，P2 维持未通过。随后才启动独立策略的严格离线完整桌赛和赛事评测，不以本接口的局部对拍代替强度或发布门禁。

本方案不调用线上服务。规则变化须补官方金例或 `fan-calc` 对拍；无官方裁决依据的组合只能保持 `blocked` 或条件假设，不能写成已确认规则。

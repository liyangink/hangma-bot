# T127：S02精细性能诊断与优化依据

**2026-10-04，先诊断、未实施新优化。** 同一T123执行装配的9次完整选择，输入摘要、全合法分数、解释和操作计量全部等同S02原参考。主要成本是条件图构建中的事实分析、状态推进和对象处理；完整输入转换及受限执行器也占可观时间。相容牌码计算和递归入口自身不是首要热点。源码、规则、覆盖范围和生产接线均未改，仍无VIP上线资格。

## 细计时纠正了什么

**把函数累计时间、递归叠加和调用次数直接当成优化优先级，会产生误导。** 本轮用选定调用边界的嵌套时钟，另以普通弃牌和重摸打为控制。空函数校准约469ns额外开销/调用，仅用于认识插桩影响，不从实际测量中扣减。数据不是随机交错性能比较。

| 极端响应中的选定边界 | 次数 | 诊断计时 | 解释 |
| --- | ---: | ---: | --- |
| 等待态事实整体 | 8812 | 687.5ms | 含以下事实分析、构造校验等，不与子项相加 |
| 真实手牌向听/进张核心 | 6659 | 160.6ms | 不含外层手牌汇总；含规则数学调用 |
| 公开未见牌计数入口 | 10991 | 151.7ms | 公开输入校验、缓存查询与计数 |
| 等待态构造校验 | 4504 | 133.2ms | 包含语句计时开销，不授可节省量 |
| 对象复制replace | 41764 | 180.3ms | 含被复制对象的构造校验；排除其他已选子边界后124.2ms |
| 路线结构分析入口 | 4504 | 110.3ms | 含内部缓存和目标计算 |
| 自然面子准备入口 | 4504 | 78.7ms | 与普通路线事实分别计算 |
| 相容牌码计算 | 22825 | 73.1ms | 含手牌计数；首轮较粗计时63.6ms |
| 完整原始值转换candidate_view | 2 | 162.6ms | 录制和评分各一次，位于前置之外 |

旧T125原生函数剖析把相容码累计显示为1.609秒；本轮低开销边界计时仅约64—73ms。原生函数级剖析对大量生成器/调用的影响很明显，不能把旧值当作真实可回收成本。它可以提供调用关系，但必须与低开销计时和栈采样交叉核对。

递归构图入口`replacement`、`action_choices`的累计时间会按嵌套层级重复计入，甚至大于整次建图时间。它们自身排除已选子边界后的成本较小；只改成显式循环不会消除后继事实分析、复制与校验。选定边界的“独占时间”仍包括未单独计时的内部工作，不等于cProfile函数自身时间。

## 已定位到具体语句的浪费

**等待态校验中，在规范牌序循环内反复构造同一个集合。** 冻结执行源`route_heuristic_view.py`第169—173行校验五类牌码集合，包含：

```python
codes != tuple(code for code in CANONICAL_TILE_ORDER if code in set(codes))
```

`CANONICAL_TILE_ORDER`有34种牌。每检查一个非None集合，这个表达式就重复构造34次`set(codes)`；即使空元组也会构造空集合。4504次等待态构造把这一重复工作放大。该整个语句块计时79.2ms，是133.2ms构造校验中最大的块。

这次仅在原顶层语句前后插入时钟；移除时钟节点后AST完全等同原函数，所有实际评分仍精确一致。可提出的后续修复是每个集合构造一次再按原顺序检查，保留类型、去重、错误顺序和非法输入语义。尚未实施，也不承诺能省掉全部79.2ms，更不足以独自解决时限。

## 原生CPU栈与内存证据

**原生采样已覆盖构图，热点包含Python对象操作；纯C手牌求解不占主要样本。** 最初沙箱内sample退出255，没有报告，业务仍完成；第二次移出沙箱后成功，但2097/2354主线程样本落在等待，构图覆盖不足。第三次先启动5秒采样，再固定等待2秒后执行一次选择，取得完整构图覆盖。前三份结果均保留，不将等待样本归入算法CPU热点。

对齐采样共3907个主线程栈样本，排除显式等待后1345个。按完整树的独占栈计数归类，不叠加递归累计：

| 样本归属 | 非等待样本数 | 约占非等待样本 |
| --- | ---: | ---: |
| 条件图构建 | 861 | 64.0% |
| 公式和执行器 | 175 | 13.0% |
| 输入对象转换 | 128 | 9.5% |
| 编码/压缩 | 153 | 11.4% |
| 未分类Python及测量收尾 | 28 | 2.1% |

另一种按栈顶操作分类看到：对象分配/释放195个样本，属性查询/哈希/比较138个，Python字节码277个，C手牌数学66个。Cython生成代码及其他原生工作仍有575个，不将它们全部武断归为Python调用开销。样本里有`tupledealloc`、`_PyObject_Malloc`、`_PyObject_Free`、`PyObject_GenericGetAttr`等具体符号及生成C行号。这是原生调用栈定位，不是硬件缓存未命中、内存带宽或CPU指令计数；那些尚未测量。

内存跟踪单独运行，8层Python分配栈明显增加耗时，整次75.3秒不能当运行性能。构图就绪时受跟踪存活量27.54MB、峰值32.43MB；记录与评分阶段峰值113.40MB。它记录的是受跟踪对象及快照，不包含全部原生分配，不能把追踪进程269MB峰值当作正常生产内存基准。原生采样报告本进程physical footprint约171MB，也只是一条诊断进程观察。

返回后部分图仍存活：研究装配的`CanonicalProjection.instances`强持有各次投影，以便退出后保存缓存统计。不能把这种诊断保留直接判为生产泄漏；正式装配前必须单独审查其生命周期。快照只给存活量/净差，不是总分配流量；Cython内部不少分配归到Python调用位置，尚不能全部精确落到C分配语句。

不启用tracemalloc的深计时另记录711次GC、总暂停109.9ms、最大25.6ms。GC是部分成本，不能据此禁用GC或把分配/释放与GC视为同一件事。原生栈中的直接引用释放也产生工作。

## 后续优化准则

**先提出绑定热点的单项假设，验证后再纳入；不直接全面改写递归或数学后端。** 优先级如下：

1. 修复已定位的重复集合构造，保持完整校验和错误语义，先差分再实测。它是具体浪费，但预期量级有限。
2. 拆清重复输入转换、执行器全图检查及临时对象的成本，研究更少物化与复制的表示。保留候选容器隔离、严格计量和完整审计，不能直接共享可变字典。
3. 针对事实分析和状态处理，分别研究能共享的不可变事实、计数表示、对象构造和公开校验；资格、领取身份、牌码容量和墙余必须保留。不以手牌相同替代条件相同。
4. 相容码复用降为次级优化。显式任务栈主要服务预算控制和并发隔离；迁移更多C代码需先明确会减少哪些对象操作及Python边界，不能仅以“已经编译”判断有效。

每项登记预期减少的具体调用或分配；数学通过后，用原面板和冷/热明确的受控计时验证端到端收益。若收益不足，保留负结果并回到剖析，不沿用未经确认的加速装配。真实计算服务、M场并发和官方门仍未完成。
